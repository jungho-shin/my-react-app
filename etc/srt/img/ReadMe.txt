시간 흐름에 따른 메모리 변화
4분 ① — Spark Connect 클라이언트가 첫 세션을 만들면 executor의 isolatedSessionCache에 ClassLoader가 등록됩니다. 정상 동작. 빨간 선과 초록 선이 동일하게 ~130 MB로 올라갑니다.
20분 ② (GC 추월 시작) — 약 10개 세션이 생성/종료된 시점. 수정 전에는 세션 종료마다 URLClassLoader.close()가 호출되지 않아 JAR 파일 핸들과 클래스 메타데이터가 heap에 잔존합니다. GC가 일부 회수하지만 새 세션이 만드는 메모리 증가 속도를 따라잡지 못해 빨간 선이 우상향으로 꺾이기 시작합니다. 초록 선은 세션 종료마다 메모리가 깨끗하게 회수되어 100~150 MB 사이 톱니 패턴을 유지합니다.
36분 ③ (위험 영역) — heap 사용량이 768 MB(75%)를 넘어 차트의 빨간 음영 구간으로 진입. 이때부터 Full GC가 빈발하면서 태스크 처리 지연이 눈에 띄게 발생합니다.
50분 ④ (OOM) — heap 한계(1024 MB) 도달. java.lang.OutOfMemoryError가 발생하며 executor 프로세스가 중단됩니다. 진행 중이던 모든 태스크 실패. 반면 같은 시점에 초록 선은 여전히 ~140 MB로 평온합니다.
실제 환경에서 이 50분이라는 숫자는 변수가 큽니다. 세션당 JAR 크기, 동시 세션 수, executor heap 크기, GC 알고리즘에 따라 OOM 도달 시점이 분 단위가 될 수도, 일 단위가 될 수도 있습니다. PR 본문에서 cloud-fan이 언급한 SparkConnectJdbcDataTypeSuite처럼 메모리가 작은 CI 환경에서 빠르게 세션을 생성/종료하는 경우 가장 빨리 재현됩니다.
